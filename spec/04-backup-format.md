# 04. Формат резервной копии (контракт между платформами)

Файл бэкапа — **единственный способ перенести данные** между iOS (PWA), Android и web.
Любая реализация обязана:
- экспортировать файл, который принимают все остальные;
- импортировать файл, созданный любой другой реализацией той же `schemaVersion`.

Эталон проверки — `src/domain/backupValidation.ts` (PWA), машинное описание — [`schema/backup-v2.schema.json`](../schema/backup-v2.schema.json),
примеры принятых и отклонённых файлов с текстами ошибок — `fixtures/backupValidation.json` (функция `parseBackup`).

## Структура

```json
{
  "app": "pwa-budget",
  "schemaVersion": 2,
  "exportedAt": "2026-11-05T10:00:00.000Z",
  "data": {
    "accounts": [ ... ],
    "categories": [ ... ],
    "budgetLimits": [ ... ],
    "transactions": [ ... ],
    "debts": [ ... ],
    "goals": [ ... ],
    "config": [ { "key": "fx_rates", "value": { "rates": { "USD": 503.12 }, "date": "2026-11-05", "source": "nbk" } } ]
  }
}
```

- `app` — всегда `"pwa-budget"` (историческое имя; Android пишет то же значение).
- `schemaVersion` — `2`. Импорт принимает **только** совпадающую версию.
- `exportedAt` — ISO-8601, момент экспорта.
- Таблицы — массивы записей с полями из [01-data-model.md](01-data-model.md). Необязательные поля без значения
  **опускаются** (не `null`).
- `config` в экспорте содержит **только** `fx_rates` (если курсы заданы). Остальные ключи локальны.
- Порядок записей в массивах не важен.

## Правила проверки при импорте (по порядку)

| # | Проверка | Сообщение |
|---|---|---|
| 1 | Корректный JSON | «Файл не является корректным JSON» |
| 2 | Корень — объект, `app == "pwa-budget"` | «Это не файл резервной копии приложения» |
| 3 | `schemaVersion == 2` | «Неподдерживаемая версия схемы: {версия}» |
| 4 | `exportedAt` — строка | «Нет даты экспорта» |
| 5 | `data` — объект | «Нет блока data» |
| 6 | Каждая таблица (кроме config) — массив | «{таблица}: ожидался массив» |
| 7 | Каждая запись — объект | «{таблица}[{i}]: ожидался объект» |
| 8 | Поле-перечисление в списке значений | «{таблица}[{i}].{поле}: недопустимое значение» |
| 9 | Число — конечное число | «{таблица}[{i}].{поле}: ожидалось число» |
| 10 | Строка/логическое — нужного типа (необязательное может отсутствовать) | «{таблица}[{i}].{поле}: ожидался тип string \| boolean» |
| 11 | `id` уникален в таблице | «{таблица}: повторяющийся id {id}» |
| 12 | `config` — массив объектов с `key` (строка) и `value` | «config: ожидался массив» / «config[{i}]: некорректная запись» |
| 13 | `accountId` и `toAccountId` операций ссылаются на существующие счета | «transactions: ссылка на несуществующий счёт ({id операции})» |

Таблицы проверяются в порядке: accounts, categories, budgetLimits, transactions, debts, goals, затем config;
поля — в порядке, указанном в схеме. Первая найденная ошибка прерывает проверку.

**Чего проверка не делает** (и не должна делать, чтобы не отклонять файлы друг друга):
- не проверяет формат дат и цветов, ссылки на категории, долги и цели;
- **не отклоняет лишние поля** — их можно игнорировать при импорте (так добавляются поля в будущем без смены версии).

## Совместимость и эволюция формата

- Новое **необязательное** поле — без смены `schemaVersion`. Старые версии его игнорируют.
- Новое обязательное поле, переименование, смена смысла → новая `schemaVersion`, и импорт обязан
  уметь читать предыдущую версию (миграция при импорте). Изменение формата делается **сначала в этом
  репозитории** (документ, схема, фикстуры), потом во всех реализациях.
- Числа пишутся как JSON-числа (double). Целые суммы — без `.0` желательно, но импорт принимает любое число.
- Кодировка UTF-8, без BOM.
